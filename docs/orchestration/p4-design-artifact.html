01 The gap, as one path

Phases 0–3 shipped the machinery. A worker CAN report — write_result is the sanctioned, no-confirm, own-board-bound self-report channel. What is missing is everything after the recording. The path stops in a Map.

worker terminal └─ write_result {status, summary, refs[]} (MCP, worker tier, NO human confirm) └─ mcpBoot.ts:109 recordResult → recordBoardResult(id, result) └─ boardResults.ts:13 const results = new Map<string, BoardResult>() ├─ read by canvas://board/{id}/result ← only if an agent asks ├─ read by awaitSettled ← only if someone is blocked on it └─ read by boardResultSynth ← only on salvage ✗ no push to the renderer ✗ no board renders it ✗ no toast, no ring, no OS notification

The one exception (the DISPUTED→corrected A7 claim): a worker dispatched through the Command board surfaces in its recap TIMELINE, because that dispatch parks awaitSettled on it and snapshots the result onto its own task. A worker an external orchestrator spawned has no such task — nothing is waiting, so nothing is shown. That is the whole of P4's problem.

Second dead end: two attention buckets with no producer

02 What P4 builds — and the confirm budget that shapes it

The load-bearing constraint: high-frequency N-worker status must never be a durable content write. Every add_card / add_planning_element is human-confirmed, so streaming status as durable content fires N confirm prompts at exactly the scale the feature exists for. Every row below is chosen so the confirm column reads 0 except once.

Signal Frequency Channel Durable? Human confirms
worker status change high — N workers × many transitions commandFeed McpCommand → commandStore (ephemeral) no 0
worker write_result 1–3 per worker same commandFeed — result zone on the card no 0
worker blocked / needs you medium attention ring + badge + OS notify + canvas://attention no 0
merged findings once, at end of run batch modal → ONE patchKanban carrying N add ops yes 1 (for all N)

Nothing else is added. If a design makes the human click N times for N workers, it is the wrong design — this table is the test every decision below has to pass.

P4 adds three edges, no new sync path: worker write_result ──▶ recordBoardResult (unchanged) │ ├─▶ ① observeBoardResult(id) ──▶ sendMcpCommand{ commandFeed } ──▶ useMcpCommands ──▶ commandStore ──▶ Command board │ the ONE canvas write pipe — S1/S2/S3's rule, fourth lane running └─▶ ② classifyAttention(result, ledgerTag) ──▶ lifecycle deliver ──▶ ring · badge · OS notify · canvas://attention end of run ────────────────▶ ③ composeFindings(boardResults + ledger) ──▶ BatchConfirmModal (N rows, 1 gesture) ──▶ patchKanban[N adds]

03 D1 — how an external worker renders on the Command board

The Command board already is the lifecycle kanban with per-task result zones. The question is only where a worker nobody dispatched from here lands.

A · Same five columns, ext chip recommended

A fed worker becomes a normal task in Queued→Done, marked with a blue ext chip and carrying no local controls (no ⚙, no ↻ — we did not spawn it, we cannot retry it).

  • Why: the columns already encode exactly this lifecycle. One surface, one scan.
  • Why: zero change to tasksInColumn / recapBuckets — a fed task flows into the recap NOW/TIMELINE for free.

B · Separate "External" lane below

A second row of cards under the kanban. Cleanly separated, but it doubles the board's height budget and splits "what is running right now" across two places the eye has to join.

C · A sixth column

Rejected: the column axis is lifecycle, not origin. A sixth column would put a finished external worker in a non-Done column and make the counts lie.

Four things in that mock are load-bearing, not decoration: the ext chip (you always know what you did not dispatch); claimed · not verified on the settled card (S2's rule — the UI never launders a worker's claim into a verification); the unrecognized status "partial-ok" — treated as unsettled line (the off-vocabulary fallback, stated in the visible string); and +3 more workers not shown · feed cap 50 (a silently-capped feed reads as "nothing happened", which is worse than no feed).

The lookup discipline (the S2 and S3 [critical])

A worker board is reused: the orchestrator hands the next task to whoever went idle, so one board id matches several tasks. externalTaskFor(tasks, boardId) scans newest-first and prefers a non-terminal task — mirroring swarmLedger.taskForBoard exactly. A first-match scan would pin every later report onto the board's first-ever task; that is the identical bug S2 shipped a fix for and S3 hit again.

When there is no Command board on the canvas

4 external workers are reporting. Add a Command board to watch them — their status is already being collected.

The Command board is user-created and singleton. commandStore is a global store, so the feed fills it regardless — when the human adds the board it is already populated, nothing is lost. One toast, once per session, so the absence is never silent.

04 D2 — waking the two dead attention buckets

The ring, badge, OS notification and canvas://attention machinery all exist and all work. What is missing is a producer. P4 adds one, plus one new attention kind so the declared-but-unproduced blocked bucket finally has a source.

A · Add blocked as a fourth AttentionKind recommended

needs-input keeps the pulsing warn ring (act now — it is asking you something). blocked gets a steady warn ring (stuck — look when you can). Different urgency, same colour family, no new palette.

  • Unlocks boardStatusBucket → 'blocked', which agents read over canvas://attention. Half the P4 ask is exactly this bucket.

B · Reuse needs-input for everything

Cheaper — no vocabulary change, no CSS. But the blocked bucket stays dead forever, a stalled worker and a worker asking you a question look identical, and the roadmap's "route blocked/awaiting-review through attention" is only half done.

The detection, and where it comes from

Two producers, both host-side, both reusing classification that already exists. P2's swarmWatch already decides blocked / lost / stalled — P4 wires that decision to the ring rather than inventing a second notion of blocked.

Source Trigger Attention kind Bucket
write_result status ∈ blocked / needs-input / waiting needs-input awaiting-review
write_result status ∈ done / ok / success done (normal derivation)
write_result status ∈ failed / error error failed
ledger tag needs_input · unreviewed · merge_ready needs-input awaiting-review
ledger tag lost · stalled · failing_check · dependency · overlap · dirty_worktree blocked blocked
fallback anything off-vocabulary blocked blocked

Why blocked is the safe fallback: the failure mode to avoid is silence. Falling back to done would launder an unknown state into success; falling back to error would claim a failure that was never reported. blocked claims only "this worker is not making progress and I could not classify why" — which is true, visible, and reversible by the next report.

No notifications-config schema change. The OS/toast layer stays gated by the existing onInput / onError / onDone switches — a blocked worker rides the existing needs-input lifecycle event through gateNotification, and only the on-canvas kind carries the finer distinction (an additive optional field on the notify:lifecycle payload). No new settings row, no config migration, no default to pick.

05 D3 — the batched findings write your call

This is where the no-confirm-storm promise is kept or broken in front of the user. Today add_card is one card, one confirm — 12 findings from 4 workers is 12 modals. The good news: the batch gate is already built and shipped. BatchConfirmModal (one modal, N rows, per-row checkbox, Deny-all, Esc denies all) has been carrying relay_prompts since T4, and the renderer's patchKanban applier already takes ops: KanbanOp[] — N adds in one command. Neither needs new code.

Three ways to trigger it — and the one that needs your decision

A · Human-triggered ship regardless

A Publish findings → action on the Command board. MAIN composes the batch from the results it already holds, shows the modal, writes one patchKanban.

  • Zero wire change, zero package publish, zero new tool.
  • Reuses BatchConfirmModal + the existing kanban applier verbatim.

B · Also agent-triggered needs your OK

A new publish_findings MCP tool so the orchestrator can initiate at end of run. The agent names only the destination board + lane — MAIN re-derives the findings from its own results Map, so the agent cannot fabricate a card ("the reply proposes, MAIN disposes").

  • Cost: publish @expanse-ade/mcp → exact-pin bump → parity lockstep, one PR per repo. Same composer + same modal as A — it is a thin tool on top.
  • This is the only thing in P4 that touches the broker wire.

C · Reuse visualize_plan rejected

One call, one confirm, N items — already exists. But PlanItem has no ref / fileRefs / description, so every finding loses its file:line; and it creates a new board per publish instead of accumulating on one findings board.

Recommendation: ship A now, and B in the same PR if you approve the package publish. A is a strict subset of B — same MAIN-side composer, same modal, same single write — so if the publish is gated, P4 still fully closes the gap for the human and B becomes a small follow-up. The roadmap's proof sentence ("the orchestrator re-surfaces… findings land as durable kanban cards") is only literally met with B.

06 Closed vocabularies + the safe fallback for each

SWARM_BLOCKED_TAGS, SWARM_TRIAGE_ACTIONS and SWARM_WORKTREE_DISPOSITIONS set the precedent: a closed vocabulary gets an exhaustive test including an off-vocabulary case, and the fallback must be the safe value. P4 adds three.

Vocabulary Members Off-vocabulary fallback Why that is safe
write_result status
→ TaskStatus		 done/ok/success → done; failed/error → failed; blocked/needs-input/waiting → stays executing + blocked chip reporting Non-terminal, so the card stays in the recap's NOW zone and the human keeps watching. Never claims done, never claims failed.
SwarmBlockedTag
→ AttentionKind		 see §4 table (9 tags, 2 destinations) blocked Surfaces rather than hides. The only outcome worse than a wrong ring is no ring.
AttentionKind
→ BoardStatusBucket		 needs-input → awaiting-review · blocked → blocked · error → failed · done → (normal) no override An unrecognized kind falls through to liveness derivation — it never fabricates a state the runtime cannot support.

08 What P4 does NOT build

  • Autonomy tiers — confirmPolicy, session-consented, per-role env deny/allow-list. All base Phase 5. Observability lands before autonomy relaxations; that is the entire sequencing argument.
  • Orchestrator re-attach — base Phase 5. P2's clean-shutdown v1 stands.
  • The S4 lane — docked lead-terminal chat, cost metering / budget ceiling. Different "4".
  • Making the Command board persistent or non-singleton — it is ephemeral + singleton by design. P4 adds a feed, not a re-architecture. If commandStore starts getting serialized, something went wrong.
  • Auto-merge of worker branches — P3 surfaces branches for human merge and that stands.
  • A second canvas sync path — the feed rides MAIN sendCommand → useMcpCommands → canvasStore, the one pipe, now for the fourth lane running.
