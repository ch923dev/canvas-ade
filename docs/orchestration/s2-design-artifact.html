Run ledger + triage — making a swarm run survivable instead of a demo

lane feat/swarm-s2 · base 19b1f2a7 (v0.34.0, S1 = #386) · target 0.35.0 · rides base Phase 2 (04-roadmap.md) · specs 07-swarm-board.md §3/§4/§6 · 03-mechanism.md 6–8 · 09-progress-recap.md §3/§4

1What S2 actually changes

S1 shipped the surface. Every fact it renders — the chat transcript, worker membership, statuses, results — lives in the ephemeral per-board swarmStore and MAIN's in-memory SwarmSession, and dies with a reload. S2 adds the durable half (a host-side run ledger), the failure model on top of it, and the triage surface that makes both visible and actionable. Three regions change visually; one new thing is invisible until something goes wrong, which is exactly when it must be legible.

Region S1 (shipped) S2 (this gate)
2 · plan strip Read-only chips projected from the run's Planning board. Click = jump. Trailing note literally reads “editing → S2”. Editable mid-run. Each chip gains a real checkbox, inline rename, remove, and a trailing ＋ add chip. A chip owned by a live worker carries that worker's state dot. Human edits are direct; orchestrator edits stay gated.
3 · worker cards Five states: needs-input / working / done / error / idle. Timer + role badge + activity line. Two new states — stalled (nominally running, nothing has moved) and lost (died mid-task, result salvaged). Each carries a mono disclosure line: the threshold that fired, or the provenance of the salvaged result.
4 · needs-you strip A flat jump list of run workers carrying an attention mark. One action: Open ▸. Head literally reads “approve/deny · batching · stall watch → S2”. A real triage queue. Risk-ordered rows from two sources (attention marks + ledger state), each with a closed-vocabulary blocked tag and inline actions (Reassign / Accept / Open / Dismiss). Taller (132→196px), counted, scrollable.
5 · header Run timer + Pause all. Adds one chip: restored — this run came back from the ledger after a reload, with what survived.

The exit proof this design has to serve (07 §6): kill a worker mid-run — the board shows the stall, the orchestrator salvages/reassigns, and the chat narrates it. Reload the app mid-run — the ledger restores the run. Every pixel below is in service of one of those two sentences.

3Region 2 — the plan strip becomes editable

S1's chip is one button: click = jump to the Planning board. S2 needs four verbs (tick, rename, remove, add) without losing the jump and without letting a stray click silently rewrite the plan of record mid-run. The answer is to split the chip into spatially distinct hit targets rather than adding a mode.

Who may edit, and what it costs

Actor Gate Why
human direct It is the human's own board and their own plan. A confirm modal for “did you mean to tick that box?” is the approval-flooding anti-pattern (07 §4.7) and would train the click-through reflex that buries the real decisions. The write goes through the Planning board's normal undoable edit, so a mis-tick is one ⌘Z away.
orchestrator confirmed Unchanged from every other MCP write — an agent-proposed plan edit is human-confirmed before it lands, and MAIN re-validates the proposal. “The reply proposes, MAIN disposes.”
Decision D2 needs your nod. The alternative to the always-live checkbox is an explicit edit mode: an Edit button at the right of the strip; off = S1 exactly (chips are inert jump buttons), on = checkboxes and rename go live and a Done exits. It is strictly safer against stray clicks and costs one extra click per tick. Recommendation: the always-live checkbox above — ticking is the highest-value, most frequent action, the three hit targets are spatially unambiguous, and the edit is undoable. Say the word and it becomes a mode instead.

4Region 3 — two new worker-card states

Every card gains a third line: a mono disclosure line under the activity line. It is where the threshold that fired, the provenance of a result, and the reason a failure failed all live — because the statusline renders summary only, and an S1 eyeball bug proved that a reason not carried in the visible string is a reason that does not exist.

State Signal Rule
working solid --accent dot, pulsing Unchanged from S1.
needs-input --warn dot + ring, --warn card border + wash Unchanged from S1, and nothing else is allowed to borrow this language. Amber on a card means exactly one thing: a human is the blocker.
stalled new hollow --accent ring, frozen (no pulse) + the timer turns --warn Border stays neutral. The honest reading is “nominally running, nothing has moved” — so the dot keeps the working colour but stops moving, and the timer is what goes amber. The disclosure line names the threshold inline: stalled 18m · threshold 10m — a disclosed cap, never a silent one (06 §2). It is kept deliberately terse because the card grid's minimum column is 180px and a truncated disclosure discloses nothing.
lost new hollow --err ring, --err border + wash, timer — The worker died mid-task. Hollow (not solid) because it is absent, not erroring. The disclosure line carries the exit reason and the salvaged result's provenance, which is always derived when the worker never self-reported.
done solid --ok dot, card at 85% opacity Unchanged, and the S1 provenance split stays: “agent-claimed, unverified” vs “derived from transcript”. S2 never upgrades a claim to a verification.

5Region 4 — the needs-you strip becomes a triage queue

S1's strip answered one question (“which board has an attention mark?”) with one verb (“open it”). The queue answers the harder one: what should I deal with, in what order, and can I deal with it from here? Rows now come from two sources, carry a closed-vocabulary tag you can write a rule against, and end in actions rather than a jump.

Ordering is risk, not time

  needs input    a human is the blocker RIGHT NOW              amber row      → Open ▸
  lost          a worker died; its work needs a decision      red row        → Accept · Reassign
  failing check a claim did not survive its acceptance check  red row        → Dismiss · Reassign
  stalled       past the threshold, still nominally alive     neutral row    → Wait · Reassign
  dependency    blocked on another task's result              neutral row    → Open ▸
  unreviewed    a claimed-done result nobody has looked at    neutral row    → Dismiss · Open ▸
  done + seen rows leave the queue entirely — the queue is work, not history.

The tags are a closed vocabulary (09 §3: “you cannot write a triage rule against a paragraph”) — needs_input · lost · failing_check · stalled · dependency · unreviewed. They are ledger fields, so the ordering is mechanical and testable rather than a heuristic over prose.

What each action actually does

Action Behaviour
Open ▸ S1's jump — camera-fit + select the worker's real terminal board. An answer to a needs-input question is typed into that terminal. S2 deliberately does not add a reply box here: forking terminal input would fork terminal behaviour, which the Q11 lens model exists to prevent.
Reassign Asks the orchestrator to re-dispatch this task to a fresh or existing worker. Goes through the normal dispatch confirm — the button is a request, MAIN re-validates and the human still approves the actual write. The chat narrates it in the orchestrator's voice.
Accept Marks a salvaged result as good enough — the ledger records the human's acceptance (provenance stays derived; acceptance is not verification), and the row leaves the queue.
Wait / Dismiss Snoozes the row. Wait resets the stall clock once (and says so); each is recorded, so “I already looked at this” survives a reload.

Batched confirms — no new modal

“Batched confirms” and “the triage queue” are two different mechanisms and the design should not blur them. The queue holds state that needs a decision. The batch confirm is how a multi-dispatch round is presented: instead of four sequential modals for a four-worker fan-out, the orchestrator's plural dispatch raises one per-row modal — which already exists and ships today for relay_prompts. S2 reuses it verbatim.

Note what the queue therefore does not get: a “Review N pending ▸” launcher in its header. A batch confirm is raised by the dispatch round and blocks it; there is nothing for a launcher to open when no round is in flight, and when one is, the modal is already up. A button that is inert most of the time and redundant the rest of the time is worse than no button. (Multi-selecting queue rows to batch several reassigns into one confirm is a real idea — and deliberately out of scope here.)

Batching does not weaken the gate. Each row still runs the shared write gate independently — its own single-use nonce, its own TOCTOU re-check, its own audit row — with the human's per-row decision fed in. One approval is still exactly one sanitized command line. This is the identical discipline mcpRelayBatch.ts already enforces; S2 adds the swarm caller, not a new gate.

6The invisible half — the ledger, and what “restored” looks like

The ledger has no UI of its own. It earns its keep in exactly one visible moment: you reload the app mid-run and the board comes back instead of coming back empty. That moment has to be honest about what survived — the run's facts survive; a dead worker's live PTY does not.

One file per run rather than one file for all of them, because the run id is the swarm board id — so restore is a filename lookup, the existing isSafeId path guard applies verbatim, and a corrupt ledger poisons exactly one run instead of every run in the project. Written through canvasMemory's existing atomic writer, so run ledgers inherit the recap sidecars' commit behaviour exactly: ignored by default, versioned alongside memory/ when the project has opted in to committing canvas data (ADR 0009).

Constraint How it is honoured
scene/session split Zero new board-schema fields. No PATCHABLE_KEYS change. No schema bump. The ledger is a separate sidecar, exactly like mcpPendingCommands. The persisted SwarmBoard stays BoardCommon only.
MAIN owns the truth The renderer's swarmStore stays the live mirror; MAIN's ledger is durable truth. Restore and every subsequent update push over the existing swarm:runEvent channel — no second sync path is invented.
the reply proposes, MAIN disposes Every renderer-originated mutation (plan tick/rename/add, Reassign, Wait, Accept, Dismiss) is re-validated MAIN-side against the ledger before it lands. S1's spawn_worker re-validation of the dialog commit is the worked example.
contract types Every new MAIN⇄renderer shape lands in src/shared/mcpTypes.ts (or a sibling swarmLedgerTypes.ts under the same rule) so a field drift is a compile error — plus a real-channel integration test, not two stubs facing each other.
degrade, never throw A missing or corrupt sidecar degrades to “no runs” and is rewritten clean on the next write — the mcpPendingCommands discipline. A poisoned ledger must never block boot.

The two failure cases, as the board renders them

Case Detect → salvage → recover → narrate
A · worker dies mid-task Detect the board leaving the mirror, the PTY exit, or a failure settle. Salvage by reading the result boardResultSynth already derived from the transcript — S2 reuses that machinery and rebuilds none of it. Mark the ledger task failed + blockedTag: "lost" with the salvaged result at provenance: "synthesized". Recover by re-queueing — the human sees a lost card, a red triage row, and the orchestrator's own sentence in chat. One voice; no raw worker output ever reaches the spine.
B · orchestrator dies with live workers v1 = clean shutdown. On swarm-board close / app quit, MAIN drains: salvage every un-settled worker's current result into the ledger, mark the run interrupted, and preserve. Re-attach is Phase 5 and explicitly not this lane. See decision D5 — the shutdown deliberately does not kill the worker boards.

7Decisions — signed off

Eight calls. Three were marked as needing the user's nod; all three are now settled (signed off 2026-07-26, surface approved as drawn). D1 was decided against my recommendation — the ledger is project-scoped, not userData — and the schema in §6 reflects the decision, not the proposal.

# Decision Rationale · what it diverges from
D1 Ledger lives with the project — <project>/.canvas/memory/run-<boardId>.json signed off Decided by the user; overrides my userData recommendation. Takes 09 §7 Q14's written default: runs are project-scoped and should travel with the project folder, and the file sits beside the board recap sidecars it is a sibling of. It therefore rides canvasMemory's existing atomic writer + isSafeId path guard rather than a new file module, and inherits the recap sidecars' commit behaviour (ignored by default, versioned under the ADR 0009 opt-in). What I gave up by being overruled: it no longer survives a git clean of an opted-in project, and it is one more thing in the user's folder. What it buys: a moved or renamed project keeps its runs, which userData keying by absolute path would silently lose.
D2 Plan-strip edits are always live (checkbox + hover ⋯), not behind an edit mode your call Fewer clicks on the highest-frequency action; three spatially distinct hit targets; the edit is undoable. The alternative (explicit Edit mode) is safer against stray clicks — §3 shows both. I recommend always-live.
D3 Ledger is a reduced snapshot with a bounded event tail, not a separate append-only JSONL One file, one atomic write path, cap-bounded — the discipline the kickoff asks for. The events[] array exists in the schema now (bounded), so S3 can grow it into 09 §3's full event log without a schema break. Softens 09 §3's run-<id>.ledger.jsonl shape; S2 does not need the run narrative that motivated it.
D4 Stall threshold = 10 minutes of no ledger-observable activity, disclosed inline, not user-configurable in S2 Sits between the transcript-idle threshold (IDLE_AFTER_MS = 60s — far too eager; a coding agent thinks for minutes) and the barrier backstop (30m — far too late to be useful triage). A named constant, printed on the card and the triage row, so the cap is disclosed rather than silent. A settings surface can come later if 10m proves wrong in use.
D5 Clean shutdown preserves worker boards — it drains and salvages, it does not kill them your call Diverges from 03 item 7, which phrases the v1 fallback as “interrupt+close_board its live workers”. Two reasons to soften it: workers are ordinary terminal boards under the Q11 lens model, and closing the human's boards out from under them is exactly the silent-destructive move the repo's dirty-worktree rule refuses elsewhere. The ledger records interrupted; the boards stay; the human decides. I recommend preserve. Say so and it becomes drain-and-close.
D6 Human plan edits are direct; orchestrator plan edits stay confirmed A confirm on the human's own tick is approval flooding (07 §4.7) and trains the click-through reflex that buries real decisions. The agent-originated path is unchanged from every other MCP write.
D7 Batched dispatch = a new host-side plural modelled on relayPrompts; the batch modal is reused verbatim mcpRelayBatch.ts already proves the shape: validate every row up front, raise ONE batch confirm, then run each row through the shared write gate independently with its per-row decision fed in via confirmOverride. Host-side only — no broker wire change, no package publish, no parity lockstep.
D8 Run timestamps live in the ledger, not on the board schema 09 §6 lists persisted timestamps as S2 with “a small schema bump”. Putting createdAt / lastActiveAt / lastSeenAt in the ledger gets the same capability with zero canvas-schema change, which the hard scene/session contract prefers.

8What S2 builds — and what it deliberately does not

In this lane

  • Run ledger — .canvas/memory/run-<boardId>.json, atomic, capped, versioned; restores a run across a reload.
  • Failure case A — worker dies mid-task: detect, salvage via the existing write_result + boardResultSynth path, mark, re-queue, narrate.
  • Failure case B — orchestrator dies with live workers: clean shutdown (drain / salvage / preserve).
  • Stall detection + reassignment — counted, thresholded, disclosed; card state + triage row + a gated reassign path.
  • Editable plan strip — human and (gated) orchestrator, writing through to the Planning board.
  • Triage queue — risk-ordered, tagged, actionable, over the existing attention system.
  • Batched confirms — a plural dispatch through the shipped BatchConfirmModal.
  • Tests — unit + a real-channel integration test + e2e; full matrix at the merge gate.

Explicitly not

  • Worktree allocation, parallel-writer enforcement, overlap-detection UI — S3. S2 writes the ledger field as null and renders no chip.
  • Orchestrator re-attach to live workers — Phase 5. S2's failure model is clean-shutdown v1, stated as such on the surface.
  • Docked lead-terminal chat, session-consented autonomy, cost metering / budget ceiling — S4 / Q10.
  • Auto-merge of worker branches — deferred; branches are surfaced for human merge.
  • A reply box in the triage queue. Answering a needs-input question happens in the real terminal — forking terminal input would fork terminal behaviour.
  • Any broker wire change. Everything here is host-side; no @expanse-ade/mcp publish, no parity lockstep.
  • Any canvas schema bump. Zero new board fields, no PATCHABLE_KEYS change.
