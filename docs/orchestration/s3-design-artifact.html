Workspace isolation — a disjoint tree per writer, and the one collision that survives it

lane feat/swarm-s3 · base 8dca6370 (v0.35.0, S2 = #392) · target 0.36.0 · rides base Phase 3 (04-roadmap.md) · specs 03-mechanism.md item 6 · 07-swarm-board.md §6 S3 / §4.3 · CLAUDE.md › Git / worktrees (locked rules, verbatim)

1What S3 actually changes

Today the platform has nothing: no worktrees, no locks, a shared cwd by default, no path claims — A6, all four negatives CONFIRMED. The app is honest about it rather than unsafe: WRITE_ROLE_CONCURRENCY_CAP = 1 admits exactly one write-role worker at a time and discloses why. S3 is the lane that earns the right to delete that sentence. It gives every write-capable worker its own git worktree on its own branch, records it in the ledger S2 built, and then deals with the collision isolation cannot remove — integration — by detecting it mechanically and surfacing it for a human merge.

Three new tags — overlap (two finished workers touched the same file), dirty_worktree (a tree kept on disk), merge_ready (the merge sequence, one row per run, expandable). §4.

The exit proof this design has to serve (07 §6): three builders on disjoint areas each work in their own worktree/branch with no file races; worktree chips render on the worker cards; overlapping touched-file sets raise an overlap warning in triage; the branches are surfaced for the human to merge, in sequence, not clobbered. Every pixel below is in service of that sentence.

2The chip — three candidates, one call

A worker card is minmax(180px, 1fr) in a grid, so at a realistic canvas width it is ~200–230px. The branch name is load-bearing — it is the string the human types into git merge — so it cannot be decoration, and it cannot be the thing that gets ellipsized away. Three placements, drawn at real scale against a real card.

Variant A — inline chip, top row

Four competing items on one 224px row. The name — how the human identifies the worker — loses, and the branch is truncated to its first eight characters anyway. Rejected on the same evidence as the S2 role-badge fix (a long role squeezed the name to w-bui…).

Variant B — prefix on the disclosure line

Costs no vertical space, but the disclosure line is the one place S2 put the reason — the stall threshold, the exit code, the salvage provenance. Sharing it means a stalled isolated worker shows either its branch or why it is stalled, never both. A disclosure that gets ellipsized discloses nothing.

Variant C — its own line (recommended)

One line, one job. Appears only on a worker that actually holds a worktree, so a read-only reviewer card is byte-identical to what ships today and the grid does not grow uniformly. Card min-height 58 → 72px. Full swarm/<run8>/builder-1 rides the title attribute; the copyable form lives in the merge-sequence row (§4), where copying is the actual task.

the same three states a write worker can be in, in variant C

The trailing dim segment is the only part that changes with state, and it says the one thing a human needs from a branch at that moment: how much is in it (4 files), that it is mergeable (ready), or that its tree was preserved rather than destroyed (kept, 7 uncommitted). Composed MAIN-side beside discloseFor, so there stays exactly one source for these strings — the S1 eyeball lesson.

4Triage — three new tags in a closed vocabulary

SWARM_BLOCKED_TAGS is a closed vocabulary whose array order is the risk order the queue sorts by. S3 inserts three members. Insertion is safe on the ledger: the tag is persisted as a string, never as an index, and an older reader simply drops an unknown tag (the task survives untagged). No format bump, no minReaderVersion move — the same rule that governs worktree/branch.

# Tag Lane Why here in the risk order
0 needs_input hot A human is the blocker right now. Unchanged.
1 lost bad A worker died. Unchanged.
2 failing_check bad Reported done, acceptance disagreed. Unchanged.
3 overlap new bad Two finished workers wrote the same file. Ranked above stalled because a stall costs time and an unnoticed overlap costs work — merging blind silently reverts one of them. Uses the shipped bad (err) lane, not amber: it is a real loss risk, but nobody is asking the human a question, and amber is reserved for that.
4 stalled neutral Nominally running, nothing has moved. Unchanged.
5 dependency neutral Waiting on another task's result. Unchanged.
6 dirty_worktree new neutral A tree was preserved instead of removed. Nothing is at risk — that is the entire point of the locked keep-on-dirty rule — so it sits low; but it must be listed, because a preserved tree the human never learns about is disk that leaks and work that is silently abandoned.
7 unreviewed neutral A result nobody has looked at. Unchanged.
8 merge_ready new seq The positive end-state, so it sorts last — and it is one row per run, not one per branch, which is what keeps the queue a work list instead of a nag list. It takes the accent lane (a new modifier, .sw-tri.seq) because it is neither a hazard nor a question: it is the run telling you it is ready for you.

What each new row's actions actually do

Row Actions Semantics — re-derived MAIN-side by offers() before anything lands
overlap Open ▸ · Dismiss Open jumps to the later worker's board (renderer-side, never a ledger write). Dismiss means “I have seen this and dealt with it” — it makes no claim about the result, exactly like S2's existing dismiss. The row never merges, rebases, or edits a file.
dirty_worktree Resolve… Opens the disposition modal (§5). The default choice is Keep, and Keep is also what happens on cancel, on error, and on app quit. Nothing in this lane can destroy a tree without an explicit, named human choice.
merge_ready Show ▾ / Hide ▴ Pure renderer state. The sequence it expands is computed MAIN-side and pushed with the snapshot, so the order the human copies is the order the ledger actually holds.
A deliberate non-feature. No triage action ever runs git merge, git rebase, or git cherry-pick. The only git writes S3 performs are: worktree add (allocate), worktree remove (clean teardown), and — only behind the named human choice in §5 — commit / stash / checkout -- . + clean -fd scoped to that one worktree. Merging is the human's, in their own terminal, in the order this surface gives them.

5Teardown — the locked dirty policy, made visible

CLAUDE.md › Git / worktrees is binding here verbatim, and it was written before any of this existed: on delete with a dirty worktree, keep on disk and prompt (commit / stash / discard / keep); never a silent --force; always git worktree remove, never rm -rf. The design question is not whether to prompt — it is when, because the obvious moment (app quit) is the one moment a modal must never appear: S2's drain() is synchronous by construction, inside the quit chain, where an awaited promise is a race against app.exit.

Moment Tree clean Tree dirty
Worker board closed / deleted git worktree remove (no force). Branch always kept. Keep on disk, silently and immediately — then raise a dirty_worktree triage row. The prompt is the row plus its modal, not a blocking dialog at close time.
Task reassigned (triage) Nothing is touched. The old worker keeps its worktree and branch; the new worker gets its own. The preserved one appears in the merge sequence with its own row. See D5 below — this is stated, not left emergent.
Worker died (lost) Nothing is touched. Its tree is exactly where its partial work is, and the salvaged result's refs[] point into it. Removing it would delete the evidence S2's whole salvage path exists to preserve.
Run ends / app quits Nothing is touched. Matches S2's D5 (the drain preserves worker boards rather than closing them out from under the human). Preserved trees are re-surfaced as dirty_worktree rows on the next open — the ledger kept the branch names, so a preserved worktree is findable after a restart.
Swarm board deleted The ledger is destroyed (S2 behaviour, unchanged) — but only after its worktrees have been disposed of clean or explicitly kept. A destroyed ledger with live worktrees on disk would orphan them with no record of what they were.

the disposition modal — reached from the dirty_worktree row's Resolve…

builder-4 left uncommitted changes

Its worktree is still on disk and nothing has been discarded. Choose what happens to it — Keep is what already happened, and what happens if you close this.

● keep · default Leave the worktree at .canvas/worktrees/builder-4 on branch swarm/a1b2c3d4/builder-4. Nothing runs. It stays in triage until you deal with it.
commit · git add -A && git commit Commit all 7 files onto the worker's own branch, then remove the worktree. The branch joins the merge sequence. Message: "swarm(builder-4): preserve uncommitted work".
stash · git stash push -u Stash all 7 files (including untracked), then remove the worktree. The stash is on the shared repo stash list and is named so you can find it.
discard · destructive, second confirm Throw away all 7 uncommitted files, then remove the worktree. Commits already on the branch survive. This cannot be undone and asks again before it runs.

The file count is read live (git status --porcelain in that worktree) at the moment the modal opens, not remembered from close time — a number that is stale by an hour is a disclosure that lies. Every option names the exact git command it runs, because a modal that performs git writes on the user's repository has to be legible as such.

6Mechanics — allocate before spawn

This is the single most important sequencing constraint in the lane, and it is a trap: safeCwd in src/main/pty.ts silently redirects a missing directory to $HOME (A6-3). Allocate late and your builder writes into the user's home directory with a green status and nothing anywhere saying so. 

 spawn_worker(role: "builder")
        │
        ├─ pack.isolation === 'worktree' ?  ──no──▶  spawn as today (cwd = args.cwd)
        │yes
        ▼
 1. resolve repo   git rev-parse --show-toplevel  from the PROJECT dir
        │                 not a repo → REFUSE the spawn. Expanse never runs `git init` for you.
        ▼
 2. derive names   branch  swarm/<runId8>/<worker-slug>
        │                 path    <project>/.canvas/worktrees/<worker-slug>
        │                 collision → -2, -3, … ; the FINAL pair is what gets recorded
        ▼
 3. git worktree add -b <branch> <path> <base>      ← the only allocate-time git write
        │                 fails → REFUSE the spawn, naming git's own error
        ▼
 4. verify         statSync(path).isDirectory()
        │                 false → REFUSE. This is the safeCwd guard: never hand over a path we
        │                 have not proven exists, because the redirect to $HOME is silent.
        ▼
 5. confirm        the worker-config dialog body names the path + branch + no-node_modules
        │                 human denies → `git worktree remove` the tree we just made, then stop
        ▼
 6. facet.spawnBoard({ cwd: path })  ──▶  ledger.assignment = { worktree, branch }
Name Shape Why
branch swarm/a1b2c3d4/builder-1 Namespaced by run so two runs in one project never collide, and greppable/deletable as a family (git branch --list 'swarm/*'). Slug is the worker's own name, so the branch in the merge sequence reads as the card the human saw.
path <project>/.canvas/worktrees/builder-1 Inside the Canvas data dir per ADR 0009 (already hidden from the File Tree, already inside the isolation boundary), never a sibling of the user's project folder. Requires one small change: canvasMemory's commit-opt-in ignore body must gain worktrees/, or an opted-in project sees the checkouts as untracked noise.
base the repo's current HEAD Every worker starts from the same commit the human was looking at when the run began. Not main — that would silently rebase the whole swarm onto a branch the user is not on.
scope one worktree per worker, not per task The design says worktree-per-worker and the spawn seam agrees: at spawn_worker there is no task yet (the task is minted at dispatch_task). A worker that takes a second task keeps its tree, which is also what makes the ledger's per-assignment {worktree, branch} a plain copy needing no new field.
Locked rules honoured verbatim. git init is opt-in and S3 never calls it: a non-repo project refuses the write-role spawn with a reason, it does not helpfully initialise the user's folder — and it especially never does so nested inside a parent repo. simple-git runs only in MAIN, behind the existing frame-guarded IPC, reusing repoScopedEnv() (the GIT_* sweep that stops a hook-inherited GIT_DIR pinning us at the wrong repository) and gitDiff's byte/time bounds. Teardown drops nothing recursively: git worktree remove, never rm -rf, mirroring what remove-worktree.ps1 exists to prevent.

7The write cap — and the strings that must change with it

07 §4.3 sets the policy: ≤2 concurrent write-role workers, readers effectively unbounded. Today's cap of 1 is not that policy — it is an honest admission that isolation does not exist yet, and it says so in both refusal strings. Raising the number without rewriting the strings would ship a cap that lies about its own reason, which is worse than not raising it. So the cap becomes a function of what actually provisioned.

In-flight write workers Cap Because
All hold their own worktree 2 Disjoint trees — the disclosed policy ceiling. The remaining collision is integration.
Any one of them does not 1 That worker shares the project working tree with every other writer — the pre-S3 situation exactly, so the pre-S3 cap applies. (An un-isolated write role stays legal: cwd is advisory, and forbidding it is an open question this lane does not get to close.)

before — swarmTools.ts · dispatch_task

write cap: 1 write-role task already running and workers share one working tree until worktree isolation lands — await it first (disclose this to the human)

after — two cases, because there are now two reasons

write cap: 2 write-role tasks already running, each in its own worktree — that is the parallel-writer ceiling (07 §4.3). Await one first (disclose this to the human)

write cap: builder-3 has no worktree of its own, so it shares the project working tree with the other writer — only 1 un-isolated write-role task may run at a time. Await it, or respawn this worker with a worktree-isolated role (disclose this to the human)

before — swarmTools.ts · dispatch_tasks (batch)

write cap: this round needs 3 concurrent write-role workers but only 1 may run while workers share one working tree — dispatch the write task alone (or await the running one) and disclose this to the human

after

write cap: this round needs 3 concurrent write-role workers but only 2 may run in parallel, one per worktree (an un-isolated writer drops that ceiling to 1) — split the round and disclose this to the human

The refusal is still returned to the model as a tool error naming the cap, so the orchestrator discloses it in chat in its own voice. No silent caps (06 §2), unchanged.

8Overlap detection — and why it deliberately over-warns

A pure function over the typed reports: intersect the refs[] touched-file sets across finished workers, after they settle and before anything merges. No I/O, no clock, unit-tested directly. The entire difficulty is normalisation — two builders describe the same file from inside two different worktrees, and a naive string compare finds nothing. 

 builder-2 refs[]:  M:\proj\.canvas\worktrees\builder-2\src\main\settingsLoad.ts:42
 builder-4 refs[]:  ./src/main/SettingsLoad.ts

   1. strip a trailing :line            → …\src\main\settingsLoad.ts
   2. make relative to its own worktree  → src\main\settingsLoad.ts        ← the load-bearing step
   3. normalise separators to /          → src/main/settingsLoad.ts
   4. drop a leading ./                  → src/main/settingsLoad.ts
   5. lowercase for the comparison only  → src/main/settingsload.ts        ← display keeps the original

                            ▶ intersection = { src/main/settingsLoad.ts }  ⇒ OVERLAP
Step 5 over-detects on purpose. Case-folding every comparison finds a false overlap between Foo.ts and foo.ts on a case-sensitive filesystem where they are genuinely two files. Branching on process.platform instead would make the function platform-dependent and therefore untestable as a pure function. The asymmetry decides it: an over-warning costs a human one glance; an under-warning silently reverts somebody's work. The same asymmetry is why a worker whose refs are empty or unparseable is treated as “unknown”, listed in the sequence, and never quietly assumed disjoint.

Sequence order

Dependency order, derived from data the ledger already has: plan-item position first (the plan strip is the dependency order the human authored), then dispatch time for tasks that map to no plan item. Overlapping branches are therefore already adjacent-ordered, earlier first, and the row states the rule the human then follows — merge, re-run the role pack's acceptance.checks, rebase the next, repeat.
